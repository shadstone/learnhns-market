Wallet integration guide

Connect a Handshake wallet to LearnHNS Market’s fixed-price Shakedex listings. The market publishes offers and checks chain state; the buyer’s wallet validates, funds, signs and broadcasts the purchase, then completes finalization.

Start with buying an existing listing. Seller tools, listing renewal and in-wallet browsing can be added separately. Market accounts are optional for this public buying flow; signing keys and recovery phrases stay in the wallet.

For the Namebase team and other wallet developers

Namebase Wallet compatibility is not yet verified by LearnHNS. A wallet download link, ordinary HNS payments, Handshake auction support or ordinary name transfers do not establish Shakedex buying support. A “Buy with” option requires an agreed handoff and a tested purchase through finalization.

1. Discover a listing

Production base URL: https://market.learnhns.com. Production is Handshake mainnet. The following requests only read data; they do not connect a wallet or buy anything.

curl --fail --silent --show-error \
  'https://market.learnhns.com/api/v2/auctions?availability=available&page=1&per_page=20'

curl --fail --silent --show-error \
  'https://market.learnhns.com/api/v2/hsd/status'
  1. Read the auctions array. Pagination is one-based, per_page is capped at 100, and total is the matching count.
  2. Use availability=available for buying. The default all feed also contains pending announcements with empty proof entries; those cannot be purchased.
  3. Take the exact canonical name from the feed and URL-encode it as one path segment. Fetch /listing/<name>/proof.json and /api/v2/listings/<name>/coin.
  4. Recheck availability and chain state immediately before signing. A feed entry is a snapshot, not a reservation.

Use lowercase ASCII names, including the xn-- form for internationalized names, as identifiers. A decoded name may be displayed alongside the canonical identifier. Do not sign a different name produced by display normalization.

Check current node readiness on the status page. Market-assisted clients must check the reported network, reachability and sync state and handle unavailable data. A wallet can use its own validated full node instead.

2. Parse and verify the proof

Market accepts version 2 fixed-price proofs with exactly one entry in data. This example shows the shape only: its placeholders are deliberately not valid cryptographic values and cannot be signed, uploaded or purchased.

{
  "version": 2,
  "name": "example",
  "lockingTxHash": "<64 hexadecimal characters>",
  "lockingOutputIdx": 0,
  "publicKey": "<33-byte compressed public key in hex>",
  "paymentAddr": "<seller mainnet HNS address>",
  "feeAddr": null,
  "expiresAt": 1825718400,
  "data": [{
    "price": 42000000,
    "fee": 0,
    "lockTime": 1794182400,
    "signature": "<65-byte Shakedex signature in hex>"
  }]
}
Amounts
price is the seller payment and fee is the additional marketplace payment, both integer base units: 1 HNS = 1,000,000 units. The example pays the seller 42 HNS. Show both amounts and the wallet’s estimated network fee before approval. Keep calculations in integers; preserve the name coin’s value separately.
Lock and signature
lockingTxHash and lockingOutputIdx identify the name’s locked coin. Verify that it is unspent, is the current owner coin for this name, and matches the Shakedex script derived from publicKey. Verify the seller signature against the actual coin and transaction outputs. Shakedex uses Handshake’s SINGLEREVERSE | ANYONECANPAY signature mode; generic payment signing is insufficient.
Time and expiry
data[0].lockTime is the transaction lock time, not the listing expiry. Evaluate spend eligibility using chain consensus rules, including median time past for timestamp lock times. Optional top-level expiresAt in proof JSON is Unix seconds and controls market visibility. It does not cryptographically revoke an offer; an on-chain spend/cancellation is needed to invalidate the lock.
Feed versus proof JSON
The auction feed supplies both data and the Bob-compatible bids alias, plus display metadata. Its expiresAt is an ISO date string (UTC, sometimes without a timezone suffix) or null; proof JSON uses integer Unix seconds. Fetch the dedicated proof endpoint rather than treating the whole feed row as an uploadable proof.
Fees and network
/api/v2/fee_info returns policy in basis points (100 = 1%) and address/addr aliases. An existing offer’s payment terms come from its proof; do not rewrite signed amounts or append today’s rate again. Verify addresses against the intended network, require a valid fee address for a nonzero fee, and confirm the node’s network. Proofs may omit an explicit network field.

Treat downloaded proofs and chain-helper responses as untrusted inputs. Market checks do not replace wallet-side verification. Persist the original proof and a local fingerprint so a changed offer requires a fresh review.

3. Complete the purchase lifecycle

  1. Review. Validate the proof and current name state. Show the exact name, seller payment, marketplace fee, estimated network fee, network and buyer’s name-receive destination. Obtain approval inside the wallet.
  2. Fill. Construct the Shakedex fulfillment transaction that spends the locked name coin, pays the seller and any proof fee, and starts a TRANSFER to the buyer. Preserve script, covenant, input and output-order requirements. Fund and sign locally, then broadcast through the wallet’s node/provider. The Market endpoints below do not sign or broadcast it.
  3. Save and track. Persist the fulfillment transaction hash, proof, locking public key, recipient, network and any wallet-specific recovery data before reporting success. Keep enough durable state to resume after closing or restarting the app.
  4. Notify Market. After broadcast, the wallet or web adapter can POST the hash to /api/v2/listings/<name>/refresh-status. Market verifies canonical chain evidence; an unconfirmed or not-yet-visible transaction may not be accepted immediately. A failed status update must not cause another purchase.
  5. Wait and finalize. After the transfer confirms, wait for the mainnet 288-block transfer lockup (roughly two days; actual time varies). Construct and broadcast the Shakedex script-spend FINALIZE. Test this specifically: a wallet’s ordinary transfer finalizer may not handle a Shakedex script.
  6. Verify delivery. Confirm the finalization transaction and verify that the current name owner is the buyer’s intended wallet destination. Handle reorgs by rechecking canonical transactions and maturity before advancing state.

“Sold” is not “finalized.” Market can record a verified purchase while the name is still in transfer lockup. The transfer-status response’s finalized label means no active lockup is visible; it does not alone prove delivery to this buyer. Check the owner and the buyer’s transaction history.

Light clients need a defined chain-data trust model. The listing coin helper covers the seller’s locked coin; the wallet must also obtain its own spendable coins, name state, transaction data, finalization inputs and broadcast access. Never expose private node credentials to the website.

4. Public API reference

These routes use the Market base URL. Public reads and the chain-verified status notification below require no Market account or API key. Node/wallet RPC credentials are separate and stay private. Replace and URL-encode path placeholders.

Wallet integration endpoints and response fields
RequestPurpose / response
GET /api/v2/auctions?availability=available&page=1&per_page=20auctions, total, availability. Select buyable inventory; revalidate before signing.
GET /listing/<name>/proof.jsonVersion 2 proof object. HTTP 404 when no available listing is found.
GET /api/v2/listings/<name>/coinname, lockingTxHash, lockingOutputIdx, coin (hsd JSON).
GET /api/v2/fee_inforate in basis points, address, addr. Policy for creating offers; existing proof amounts remain authoritative.
GET /api/v2/hsd/statusreachable, network, height, progress and node metadata.
GET /api/v2/names/<name>/statusfound, nameInfo. Check current owner, name state and covenant context.
GET /api/v2/tx/<txHash>/statusconfirmed, height, confirmations, tx. Lookup can fail when the backing node lacks transaction history; use the wallet’s provider as needed.
POST /api/v2/listings/<name>/refresh-statusJSON body {"saleTxHash":"<fulfillment transaction hash>"}. On success inspect status, sold and saleTxHash; HTTP 200 alone does not mean sold.
GET /api/v2/names/<name>/transfer-statusavailable, status, blocksUntilFinalize, ownerTxHash, ownerOutputIndex. Check payload availability even when HTTP is 200.

Error handling: handle 400 (bad input), 404 (listing/data unavailable), 409 (state conflict or evidence not ready), 429 (rate limit), and 5xx (helper/verification failure). Some errors are JSON with error; do not assume every error body is JSON. Retain the transaction hash and retry status checks with bounded backoff. The refresh route is limited to 100 requests per hour per client IP; avoid tight polling and respect rate-limit responses.

A missing coin or failed lookup is not proof of a sale. Treat uncertainty as pending verification and check canonical chain evidence. The refresh route also supports GET for legacy consumers, but it can update Market state: use POST deliberately and do not use it as a read-only health probe.

5. Agree on the wallet handoff

There is no universal Namebase or WalletConnect interface assumed by Market. A wallet team must document its supported mechanism, versions and platforms. These existing adapters are references, not APIs that another wallet automatically implements.

Bob LearnHNS desktop

The existing website opens this registered app scheme. Both query values are URL-encoded; presign contains the compact proof JSON.

bob-learnhns://x/fulfillauction?name=<encoded-name>&presign=<encoded-proof-json>

LearnHNS Wallet browser extension

The current adapter checks the injected provider and capability before requesting a fill. This is the extension’s interface; it is not a Namebase API.

// Existing LearnHNS Wallet interface; requires an installed compatible build.
const wallet = await window.shake.connect();
const capabilities = await wallet.getCapabilities();
// Require capabilities.shakedexFill and wallet.fillShakedexAuction.
// Only after the user's buy action and wallet review:
const result = await wallet.fillShakedexAuction(proof);
// result.fulfillmentTxHash identifies the broadcast purchase.

A new wallet, including Namebase

Choose proof-file import, a documented desktop/mobile app link, or a browser provider. For an app link, specify whether it carries the proof or an HTTPS proof URL, payload limits, network binding, and how unsupported versions are handled. A URL-importing wallet must restrict allowed origins/redirects and request size, and verify the fetched proof locally.

Agree on an optional transaction-hash return or callback; never treat a callback as chain evidence. Restrict return URLs and correlate responses with the intended listing. A missing app, rejected request, closed wallet or failed callback must leave a recoverable state. Opening the wallet must never silently approve a purchase.

A link to namebase.io/wallet is a download/information link. It does not pass a listing into the app or prove purchase support.

6. Test before advertising support

Use isolated regtest wallets, fake names and fake HNS first. The local Market sandbox guide documents Docker setup and its limitations. All participants must use the same regtest chain; a proof from a different local chain will not work. Do not assume the public staging hostname is connected to your test node.

# From the learnhns-market repository, with Docker available:
docker compose -f compose.regtest.yaml up --build -d
python3 scripts/check-regtest-sandbox.py
# Local Market: http://127.0.0.1:18000

The smoke check verifies the sandbox infrastructure; it does not demonstrate a wallet purchase. Follow the sandbox guide for storage requirements and create a valid seller lock/proof on that same chain. Never use a production wallet profile, seed or real funds in regtest.

  • Happy path: import → verify → review price/fees → fill → confirmation → transfer maturity → FINALIZE → confirmed buyer ownership.
  • Invalid offers: wrong network, altered signature/price/payee, mismatched name or locking script, future lock time, expired listing, missing fee address, and unsupported proof shape.
  • Changing state: another buyer wins, seller cancels, name expires, or a chain reorg changes the current owner or maturity.
  • Wallet failures: insufficient funds, user rejection, missing/old app, node unavailable, broadcast uncertainty, helper timeout, or failed Market notification. No duplicate payment on retry.
  • Recovery: restart during the lockup, recover saved purchase state, finalize after maturity, and show separate broadcast, confirmed, sold and finalized states.

Before a public “Buy with” button, agree on the exact wallet release and platform, retain reproducible test results, and complete a separately authorized low-value mainnet purchase through confirmed final ownership. This guide does not authorize spending real HNS or publishing test listings to production.

7. What each team supplies

Wallet team

  • Supported version, operating systems and test build.
  • Shakedex proof verification, fill and script-FINALIZE support.
  • App-link, import or provider specification; errors and optional result format.
  • Chain-data/broadcast provider and light-client trust model.
  • Persistent recovery behavior and test evidence.

LearnHNS Market team

  • Proof/API contract and reference code below.
  • Agreed test environment and example proofs.
  • Website adapter, installation guidance and error handling.
  • Chain-verified sale tracking and finalization guidance.
  • Version-specific compatibility wording after testing.
